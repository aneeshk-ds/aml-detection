# Methodology: AML Transaction Monitoring in SQL

Version 1.0, 2026-09-13. Rebuilt from scratch on that date: 26 of 26 models, 67 of 67 tests, every number below reproduced exactly.

## The data is synthetic and 1 payment in 981 is laundering

- Source: IBM Transactions for Anti Money Laundering, HI-Small set (Altman, Kaggle). Generated by a multi-agent simulation, no real customers.
- 5,078,345 payments from 2022-09-01 to 2022-09-18, 518,581 accounts, 15 currencies, 7 payment formats.
- 5,177 payments are labeled laundering (0.102%). 3,209 of them sit inside 370 labeled attempts across 8 typologies; 1,968 belong to no named pattern.
- Almost all activity falls on 2022-09-01 to 09-10. The last 8 days hold 715 payments.

## The pipeline is 5 SQL layers in dbt on DuckDB

```
data/ (read-only CSVs)
  -> staging       stg_transactions, stg_accounts, stg_fx_rates, stg_patterns
  -> intermediate  int_transactions_usd, int_edges, int_pattern_transactions
  -> detection     6 rule models + det_transaction_flags            (Phase 1)
  -> graph         gr_pairs + 6 typology models                     (Phase 2)
  -> scoring       sc_account_risk, sc_top100 -> outputs/ranked_accounts.csv   (Phase 3)
  -> evaluation    ev_cutoff_curve, ev_flag_performance, ev_typology_recall     (Phase 4)
```

Stack: dbt-core 1.8.7, dbt-duckdb 1.8.4, DuckDB 1.1.3. 67 data tests. No Python in the detection logic. Every threshold and weight is a variable in `dbt_project.yml`.

## Staging decisions that change the answer

| Decision | Why | Evidence |
|---|---|---|
| Account key = integer bank id + account number | The transactions file zero-pads bank codes ("010"), the accounts file does not ("10") | Text join matched 0 of 496,999 sender keys; integer join matched 496,999 of 496,999 |
| Account number alone is not a key | Some numbers repeat across banks | 4 sender numbers appear under 2 banks |
| txn_id = file row order | The source has no transaction id | Verified at rows 1, 2,539,173 and 5,078,345 |
| All amounts converted to USD with implied rates | Thresholds such as 10,000 only mean something in 1 currency | Median rate from USD-paired rows; non-Bitcoin paid and received USD agree within 0.23% at p99 |
| Bitcoin USD is approximate | Implied rate spreads from 10,000 to 20,000 USD | 1,509 USD-paired Bitcoin rows |
| Self-transfers excluded from detection | 591,212 rows (11.64%), 481,056 of them Reinvestment, 11 illicit; they inflate velocity, fan and cycle counts | `exclude_self_transfers: true` |

After scoping, detection runs on 4,487,133 payments between different accounts (5,166 illicit, 0.115%).

## Phase 1 rules flag single payments

Every value below was set without looking at the laundering label.

| Rule | Logic | Parameters | Why these values |
|---|---|---|---|
| structuring_band | USD value just under the reporting threshold | 9,000 to 9,999.99 | README; 10,000 matches the US cash reporting level |
| structuring_24h | 1 account sends 3+ payments of 5,000 to 9,999.99 USD totalling over 10,000 in any rolling 24 hours | min 3 payments, floor 5,000 | Without the floor the rule flagged 25.54% of payments, mostly many small payments from busy accounts |
| pass_through | Inside a rolling 48 hours the account receives at least 1,000 USD and sends out 90% to 110% of it | 48 hours, retention under 10%, min inflow 1,000 | README window and retention; the floor removes tiny flows (median payment is 880 USD) |
| high_velocity | Rolling 24 hour outbound count above the 99th percentile of every account's peak | threshold resolved to 20 | README top 1%; strictly above so ties do not exceed 1% |
| round_amount | Exact multiple of 1,000 in the payment currency | unit 1,000 | README |
| cross_currency | Receiving currency differs from payment currency | none | README; kept as a documented negative result |

SQL techniques: range filters, modulo, window functions with `range between interval ... preceding and current row`, `union all` to stack inbound and outbound events, `quantile_disc`.

## Phase 2 typologies work on account pairs

`gr_pairs` collapses 4,487,133 payments into 647,939 directed pairs with first and last payment time. Window 72 hours for all typologies.

| Typology | Logic | Parameters |
|---|---|---|
| fan_out | 5+ new receivers inside 72 hours (new = first payment to that receiver) | k = 5 |
| fan_in | 5+ new senders inside 72 hours | k = 5 |
| gather_scatter | A fan-in event followed by a fan-out event on the same account within 72 hours | uses fan_in and fan_out |
| cycle_2 | A pays B and B pays A, pair activity within 72 hours | 1 row per unordered pair |
| cycle_3 | A pays B, B pays C, C pays A, pair activity within 72 hours | smallest key first to remove rotations |
| scatter_gather | 3+ intermediaries carry money from the same source to the same sink, second hop within 72 hours of the first | k = 3 |

Approximations:

1. Fan detectors count new counterparties, not every distinct counterparty in the window.
2. Cycle and scatter-gather timing is tested on pair first and last times. It is a necessary condition for co-occurrence, not a proof of 2 payments inside 72 hours.
3. SQL closes cycles of exactly 2 or 3 accounts. Longer loops are left for graph tooling.

SQL techniques: self joins with swapped keys, 3-way self join, `exists` with a time range, 2-hop join with `group by ... having count(distinct ...)`.

## Scoring adds fixed weights per account

risk_score = sum of weight x flag, where each flag is 0 or 1 for an account. Maximum 23.

| Weight | Flags | Reasoning |
|---|---|---|
| 3 | pass_through, cycle_3, scatter_gather, gather_scatter | Behaviour with little ordinary explanation: money moves straight through, returns to origin, or is split and recombined |
| 2 | structuring_24h, fan_out, fan_in | Suspicious in pattern, but payroll, marketplaces and batch payments match too |
| 1 | cycle_2, structuring_band, high_velocity, round_amount, cross_currency | Weak alone; they add context to stronger flags |

Weights were set before any evaluation and not tuned on labels. cross_currency stays at 1 even though Phase 0 showed 0 illicit cross-currency payments, so no weight carries label knowledge.

## Evaluation definitions

- **Illicit account:** sent or received at least 1 labeled laundering payment. 6,357 of 422,734 active accounts (1.50%).
- **Alert:** risk_score at or above the cutoff.
- **Chosen cutoff:** the lowest score whose alerts stay within 1% of active accounts, a review-capacity rule that does not use the label. Result: 6.
- **Attempt recall:** share of labeled attempts with at least 1 alerted account, since 1 alert opens a case.
- **Lift:** precision divided by the base rate at the same level.

## How to run

Full build on a Mac or any machine with Python:

```
pip install -r requirements.txt
dbt build --profiles-dir .
```

In the Cowork VM each command must finish inside 180 seconds, so the build runs in steps (measured times):

```
dbt run  --profiles-dir . --select staging intermediate          # stg_transactions 78 s
dbt run  --profiles-dir . --select det_structuring_band det_structuring_24h det_round_amount det_cross_currency det_high_velocity
dbt run  --profiles-dir . --select det_pass_through              # 29 s
dbt run  --profiles-dir . --select det_transaction_flags         # 67 s
dbt run  --profiles-dir . --select graph                         # scatter_gather 17 s
dbt run  --profiles-dir . --select scoring evaluation
dbt test --profiles-dir . --threads 1                            # 67 tests, 35 s
```

Known issue: 1 of 2 test runs with 2 threads ended in a Python fatal error (`PyEval_SaveThread`) from dbt-duckdb 1.8.4 with DuckDB 1.1.3. The same tests pass 67 of 67 with `--threads 1`. Model runs with 2 threads did not crash.
